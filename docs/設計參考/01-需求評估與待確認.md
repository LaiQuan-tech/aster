## 二、已否決的需求

### C 單拆卡機制（原模組 1）

原文：「超過即鎖定正常卡，超額時數自動轉入隱藏版 Cash 卡（C單）以符合勞檢要求」

**不實作。** 理由：
- 勞基法 §30 V/VI：出勤紀錄應逐日記載至分鐘、保存 5 年。紀錄不實在加班費/職災訴訟中導致舉證責任倒置。
- **系統化會放大風險**：人工 Excel 造假知情者少、事後難還原；資料庫會留下原始打卡時間 + 拆卡規則 + C 單對照表整條鏈，性質從「作業疏失」變成「系統性設計」。等於花錢開發一個讓自己更難辯護的東西。

**替代設計（已納入資料模型）**：
1. `work_hour_alerts` — 接近 32/46 小時預警，把決策點交還主管，不做隱藏轉移。
2. `overtime_settlements` — **工時紀錄真實完整，給付方式另表記錄**（隨薪匯款/現金/補休）。若真實需求是「現金給加班費」，這個結構完全支援，且合法。
3. 合法出口建模：補休 §32-1、變形工時（2/8/4 週）、責任制 §84-1（限定職類且需核備）。

## 三、規劃書遺漏（已補進資料模型）

| 缺項 | 為何重要 |
|---|---|
| **稽核軌跡 `audit_logs`** | 經手錢的系統沒有留痕等於裸奔；這比掃描公告更接近真正可用的法務證據 |
| **二代健保補充保費** | 複委託單次給付逾 2 萬須扣 2.11%，規劃書只提 10% 扣繳，漏了會被追繳 |
| **扣繳起扣點** | 執行業務所得（9B）每次給付達 2 萬才扣 10%，非「一律 10%」 |
| **人員異動 `project_members.left_at`** | 離職時專案轉手、未發完的分期獎金歸屬 |
| **權限分層過粗** | 會計要匯款必須知道獎金金額，但不需知道趴數/計算基礎 → 拆成兩種權限 |
| **經理跨專案隔離** | 原規劃「經理可看專案基本資訊」未限定範圍；工程業經理離職帶走客戶名單是高頻事故 |
| **匯出功能** | 老闆一定會拉 Excel，禁不掉，不如做好並納入稽核 |
| **跨年度專案** | 工程案 2–4 年，跨會計年度的營收認列與獎金結轉 |

## 四、階段排序調整

規劃書原序（薪資先行、專案財務排到年底）有兩處問題：

1. **資料模型被切碎**：模組 5 寫「獎金隨每期收回的 20% 款項同比例分期拆發」→ 獎金/請款/專案是同一組資料。等年底才設計，階段二的專案表必然打掉重來。
2. **薪資不該當起手式**：算錯錢當月出事且信任一崩推不動。

調整後：資料模型一次做完 → 出勤請假特休（不碰錢）→ 專案合約 → 請款發票入帳 → 獎金複委託 → 薪資（平行雙軌 2 個月）。

## 六、代收代付的邊界（2026-08-24 新增）

代收代付成立的前提是**只換金流、不換發票**：

| | 簽約 | 開票/認列收入 | 收款帳戶 | 性質 |
|---|---|---|---|---|
| 代收代付 | A | **A** | B | ✅ B 對 A 掛應付，事後結清或互抵 |
| 發票也換 | A | **B** | B | ⚠️ 已非代收代付，屬轉包/聯合承攬 |

規劃書原文寫「備註**實際開立收據的公司**」，字面上落在第二列。

**處理方式**：模型兩種都能存，但第二種由 trigger 標記 `requires_review`，不靜默通過。
不擋流程，只讓異常在報表上看得見——實務上真的會有合理的第二列情況（聯合承攬、分包開票），
但那需要對應的合約文件支撐，系統的責任是把它標出來讓會計/會計師去確認，而不是幫忙藏起來。

**待回頭確認**：亞斯特實務上是哪一列？如果兩種都有，各自的比例與情境為何？
