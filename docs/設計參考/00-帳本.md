## 2026-08-26 找到並修正薪資 bug（比原判斷嚴重）

原本懷疑的是「健保眷屬未裁切 3 口上限 → 多扣」，追下去發現是更根本的斷鏈：

`apps/api/src/routes/payroll.ts` 的 `SalaryRow` / `toSalaryStructure` 只映射
method / baseSalary / dailyWage / hourlyWage，**未帶入 labor_insured_salary 與
health_insured_salary**。引擎的保費計算是 `ins && salary.laborInsuredSalary ? ... : 0`，
欄位缺漏時靜默走 0 → **每張薪資單的勞保費、健保費都是 0，實發金額被高估**。

鏈上其他環節都在（寫入端 routes/salary.ts、DB 欄位、引擎計算、rule_config 的
insurance 設定），只有讀取端 mapping 沒接上。以投保 38,200 計，每人每月少扣
955 + 592 = 1,547 元。眷屬則是完全沒計入。

#### 前半（同天多次打卡）— 不是新需求，現況已支援

第 1 條已寫的理由不重複，本條補三點：

1. **本條與第 1 條的判準互斥，同時實作會打架。**
   第 1 條藏的是「累計逾 40 小時的部分」（時數門檻）；本條藏的是
   「第 3 刷以後」（次數門檻）。同一天可以滿足其一而不滿足其二，
   兩套隱藏規則疊在同一批 `punch_records` 上會產生互相矛盾的「可見紀錄」。
   這種不一致本身就是轉錄稿被逐字當規格的徵兆。

2. **兩刷上限會把正常工時也藏掉，方向是反的。**

   只留前兩刷，可見紀錄變成「09:00–12:00，當日 3 小時」。
   這不是藏加班，是把下午整段**正常工時**藏掉——對勞檢反而成為
   工資未全額給付的證據，對員工是少算薪。外出洽公、跨日班同理。
   想藏加班的需求，用次數門檻在技術上根本達不到。

3. **「隱藏」在資料庫裡不是刪除，藏不掉。**

#### 缺口一：餘額桶的 key 是曆年，不是週年（結構問題，非補功能）

```ts
// apps/api/src/services/ledger.ts:41
function requestYear(req: ApprovedRequest): number {
  const y = new Date(req.start_at).getUTCFullYear()   // ← 曆年
  return Number.isFinite(y) ? y : new Date().getUTCFullYear()
}
```

`leave_balances` 的唯一鍵是 `(tenant, employee, leave_type, year)`，`year` 是
整數曆年。**這不是少一個功能，是桶子的 key 錯了。**

具體後果：員工 2024-03-15 到職，週年制的假期年度為 2024-03-15 ~ 2025-03-14。
現況下 2024-12-01 請的假記進 `year=2024`、2025-02-01 請的假記進 `year=2025`
——同一個週年年度被切成兩個桶。**除了 1/1 到職的人，所有人的剩餘假數都是錯的。**

修正方向：`leave_balances` 改以「假期年度期間」為鍵（`period_start` /
`period_end`，或保留 `year` 但語意改為「到職後第 N 年」），
`requestYear()` 改為依 `employees.hire_date` 推算週年期間。
`hire_date` 欄位已存在（`schema/employees.ts:19`），
`seniorityDays()` 也已存在（`routes/employee-profile.ts:117`），原料齊。

> 法規面：勞基法 §38 依「繼續工作期間」計算，**週年制本就是法定原則**；
> 曆年制是施行細則 §24 的變通，須勞工同意且不得損及權益，轉換年度還要
> 比例計算。客戶選週年制是選對的；反而現況的曆年制若未經協商，本身有問題。

天數表應建成資料而非程式碼。

§38 IV 年度終結未休完之日數，雇主應發給工資；經協商得遞延一年
（施行細則 §24-1），遞延後仍未休仍須發工資。
`leave_balances.deferred` 欄位已存在，但**無任何結算邏輯**。

#### 缺口三：無薪假不會扣薪（money bug）

```ts
// packages/rules/src/payroll-engine.ts:64
export function computePayslip(

  rules: RuleConfig, expenses = 0,

```

**引擎沒有任何請假／缺勤輸入。** `method='monthly'` 時

→ 月薪制員工請 10 天無薪假，薪水一毛不少。

（`by_attendance_days` 法會因當日無工時而自然少算，但 2026-08-25 已決策
本案薪資制度為月薪，實際走的是 `monthly` 路徑。）

此缺口與 2026-08-26 找到的勞健保費 0 元屬同一類「鏈上斷一節」，但更徹底：
那次是讀取端 mapping 沒接，這次是引擎介面根本沒有這個參數。

#### ⚠️ 待確認：「無薪假」語意（與「祭師/技師」同類的失真風險）

此詞在台灣有兩個**法規體系完全不同**的意思：

| 解讀 | 法源 | 性質 |
|---|---|---|
| (a) **事假** | 勞工請假規則 §7：全年不得超過 14 日，期間不給工資 | 例行，照做即可 |
| (b) **減班休息**（俗稱無薪假） | 勞雇協商減少工時；須報地方主管機關備查、月薪制全時工不得低於基本工資、有實施期間限制 | **另一個模組**，且未報備實施即違法 |

「無薪假需**補單**」聽起來像 (a)（事後補請假單）。但這是推測。
若客戶指的是 (b)，系統設計、法遵流程與風險完全不同，**必須先確認**。

註：「補單」可沿用既有代申請路徑（`onBehalfOfEmployeeId`，HR 代員工申請），
不需新機制。

#### 加值點：§38 VI 的書面通知義務，「隨時查詢」滿足不了

§38 VI：雇主應將特休期日及未休日數所發工資數額記載於勞工工資清冊，
並**每年定期以書面通知勞工**。

「開放個人隨時查詢」是被動的，法律要的是**主動通知**。系統既然已掌握資料，
順手產出年度特休通知書即可同時滿足查詢與法定通知——這是客戶沒要求但
應該給的東西。

#### 設計建議一：Email 不該夾帶薪資明細（個資風險）

- `employees.email` 一筆打錯 → 整份薪資明細寄給別人，且**收不回來**
- 薪資屬敏感個資，批次寄送一次出錯即群體外洩
- 郵件於對方伺服器與轉發路徑留存

明細在 ESS 登入後看。**

接起來即可，**連 PDF 都不必做**。若客戶堅持附檔，則寄加密 PDF。

#### 設計建議二（最重要）：自動寄送會讓「雙軌並行」失效

本專案硬約束：「薪資模組必須平行雙軌 2 個月，逐人差異歸零才准切換」。

**自動寄送在雙軌期間絕對不能開啟**：

- 雙軌期間新舊系統數字仍在對，本就預期有差異
- 薪資條一旦寄到員工信箱即**收不回來**
- 寄出一份錯的薪資單＝直接引爆「算錯錢＝信任崩盤」——正是雙軌要防的事

→ **寄送功能必須有 tenant 級開關，預設關閉，雙軌驗證通過才開啟，
且開關變更本身要進稽核。**

#### 設計建議三：別把「寄送」掛在 finalize 上

`POST /payslips/:id/finalize` 目前**單向不可逆**（已 finalized 再呼叫回 409，
無 un-finalize 端點）。若把自動寄送掛在 finalize，該動作就變成

建議拆三段：`finalize`（核定鎖定）→ `mark_paid`（放款確認）→
`send`（對外發送，需二次確認）。本條原文的「核算與放款確認後」正好支持這個拆法。

施行細則 §14-1 要求薪資明細列出「依法令規定或勞雇雙方約定**得扣除項目
之金額**」。目前引擎的 `attendanceDeduction` 是**全勤獎金的遲到階梯扣款**
（`payroll-engine.ts:155-162`），**不是**缺勤／無薪假扣款。

→ 第 4 條缺口三（無薪假不扣薪）未補之前，薪資條會**少列一個法定應列項目**。

**但**若屬經常性給與且與工作有對價（契約明定必發、金額固定、年年照給），
實務上仍可能被認定為工資——此為高頻爭議點。

→ **設計意涵：獎金紀錄必須帶「是否列入平均工資」「是否提繳勞退」兩個旗標**，
預設值與變更理由要留痕。這兩個旗標直接決定資遣費與勞退提繳金額。

同 repo 的 `project_share_adjustments` 有。

### 第 7 條（2026-09-11）

#### 值日生輪值：不能用 schedules，這是 DB 擋住的

```ts
// packages/db/src/schema/schedules.ts
tenantEmployeeDateUnique: uniqueIndex("schedules_tenant_employee_date_uq")
  .on(table.tenantId, table.employeeId, table.workDate)
// 註解原文：makes "one schedule per employee per day" a hard DB invariant
```

**一人一天只能有一筆排班，是 DB 硬約束。** 若把值日生／總機輪值塞進
`schedules`，會與工作班別**互斥**——員工當天要嘛有工作班別、要嘛當值日生，
無法兩者兼具。

更嚴重的是結算污染：`settlement.ts` 會取 `schedules.shift_id` →
`shifts.start_time / end_time / break_minutes` 去算工時與遲到。
把「值日生」建成一個 shift，會直接改變該員當日的工時與遲到計算。

→ **必須另建輕量的 `duty_rosters`（職務輪值表：tenant / duty_type /
work_date / employee_id / note）。這不是設計偏好，是唯一索引擋住的。**
輪值不影響工時結算，兩者刻意脫鉤。

#### ⚠️ 輪值的工時陷阱（客戶問排班表時不會想到）

輪值表本身不是工時。**但輪值造成的額外在勤時間是工時**：

- 總機需比同仁早到開機／晚走關機 → 該段為工時
- **午休留守接電話 → 該段為工時**。勞基法 §35 休息時間應得自由利用；
  被要求留守待命者，該時段不算休息，應計入工時並影響加班計算。

這是實務上最常漏、且勞檢會抓的一項。

→ 設計意涵：`duty_rosters` 應可標記「本輪值是否產生額外在勤時間」及其時段，
並由該標記餵進出勤結算，而非讓輪值與工時完全無關。

#### 生日紅包：不能只做提醒，錢要有紀錄

現金給付的生日禮金屬員工所得，須併入申報（公司直接給付者屬薪資所得；
由職工福利委員會以福利金給付者所得類別不同）。少額、非現金、慰勞性質的
實物另有認定，**但現金紅包一律要報**。
※ 所得類別與免稅範圍待會計師確認，依硬約束不在此臆斷。

→ **只做「提醒」而不記錄發放金額，年底扣繳憑單會漏。**

**架構決定：生日紅包與第 6 條的三節獎金共用同一張 `bonus_payments`。**

理由不只是省工，是正確性需求：第 6 條已確認二代健保補充保費以
「**全年累計**獎金逾投保金額 4 倍」計算（`tw-tax.ts:33`）。
生日紅包若記在別處，累計金額就會少算 → 補充保費漏扣 → 被追繳。

`bonus_payments` 以 `kind` 區分（festival / year_end / birthday / project_share…），
並帶第 6 條already 提出的兩個旗標（是否列入平均工資、是否提繳勞退）。

#### 「提醒拍照留存」：要先問拍什麼，且建議以簽收為主

「拍照留存」有三種可能，性質完全不同：

| 拍什麼 | 性質 |
|---|---|
| (a) 紅包本身／發放當下 | 內部憑證，合理 |
| (b) 員工收紅包的合照 | 涉肖像權與個資法 §8 告知、§19 特定目的；存放位置、可見範圍、保存期限都要定 |
| (c) 簽收單 | 等同簽收證明，最直接 |

**更根本的問題是目的**：若目的是證明「錢確實發到員工本人手上」
（防代領／侵占），**照片是弱證據，簽收紀錄才是強證據**。

→ 建議：**ESS 電子簽收為主**（員工自己登入確認收到，有身分、有時間戳、
不可否認），**照片為輔且選填**。既更可靠，也避開 (b) 的個資問題。
儲存沿用現有私有 bucket 模式。

## 模組二：行政公告與法務備查（Notice & Contract Compliance）

> 模組一於第 7 條結束（使用者確認無第 8 條）。

### 模組二第 1 條（2026-09-11）

> 紙本簽名公告上傳與備查：公司請假與福利等公告規章，採紙本傳閱全員簽名後，
> 掃描檔案上傳至系統專區供同仁查閱[10]，不採線上單純勾選同意，以防範勞資爭議

**處置：照做。客戶的直覺是對的，但紙本有他沒想到的弱點，系統要補起來。
建議「兩者都留」而非二選一。**

#### 這是第一條客戶主動選擇更保守做法的規則

前七條的模式是客戶想省事、我們指出風險。本條相反：客戶主動放棄線上勾選、
選擇紙本簽名以防勞資爭議。**這個直覺正確，照做。** 以下是把它做對的細節。

#### 法定義務其實不是「簽名」

- 勞基法 §70：僱用 30 人以上者應訂立工作規則，報請主管機關**核備**並**公開揭示**
- 施行細則 §37：工作規則應**揭示於事業場所內顯著之處，或發給勞工**

→ **法律要求的是「揭示或發給」，不是「取得每個人簽名」。**
簽名是雇主自行加上的舉證強化手段，用來證明「該勞工確實知悉」。

客戶的真實需求因此是：**證明某位員工在某時間確實看過某一版規章。**

#### 紙本掃描的三個舉證弱點（客戶未必想到）

1. **掃描後時間資訊消失。** 掃描檔只是一張圖，無可信時間戳。
   員工可主張「簽名是事後補的」「日期由公司代填」。
2. **無法證明簽的是哪一版。** 規章改版後，舊簽名頁對應哪一版？
   無版本綁定即說不清。**而現況更糟——連「版本」這個概念都不存在（見下）。**
3. **傳閱單會遺失，且是單點失效。** 全員簽名集中於一張紙，遺失即全無。

對照之下，設計良好的線上確認舉證力其實**強於**紙本掃描：
登入身分（Supabase Auth 帳號綁定）＋ 伺服器時間戳（不可竄改）＋
**文件版本 hash**（證明看的是哪一版、內容未被替換）＋ IP/device ＋ 稽核軌跡。

**但這不是要推翻客戶的決定。** 客戶要紙本就做紙本；重點是用系統把紙本的
弱點補起來。

#### 建議設計：三層，不是二選一

| 層 | 內容 | 作用 |
|---|---|---|
| 一（法定） | **查閱紀錄**：誰在何時開過這份文件 | 證明「已發給且可取得」，滿足施行細則 §37。**這是被動 log，不是「勾選同意」**，沒有客戶擔心的問題 |
| 二（客戶要的） | **紙本掃描上傳 + 逐人簽收追蹤** | 關鍵：不能只存一個 PDF，要建 per-employee 簽收紀錄，才知道**誰還沒簽** |
| 三（補強紙本） | **版本管理 + 檔案 hash + 生效日** | 證明簽的是哪一版、內容未被替換 |

#### 不利益變更：這才是紙本簽名真正的價值所在

若公告內容涉及**對勞工不利的變更**（減少福利、請假規定變嚴），
單純「揭示」不足。實務見解：不利益變更原則上需**勞工個別同意**，
否則對不同意之勞工不生效力。

→ 規章版本應可標記「本次變更是否涉及勞動條件不利益變更」。
若是，簽收的性質就不是「已閱讀」而是「同意」，且必須**逐人追蹤到齊**。

**客戶做紙本簽名的直覺是對的——但只有在系統幫他管「誰還沒簽」時才有用。**
一張傳閱單傳完，沒人知道少了誰。這是本條最該做的功能。

#### 現況：公告表存在，但對「備查」有三個致命洞

#### ⚠️ 最嚴重的發現：請假單據現在就可以被硬刪

```ts
// apps/api/src/routes/requests.ts:1028
// DELETE /requests/:id — HR admin removes a non-approved form record.
// Approved records are retained because they may already have ledger/payroll effects.
if (lr.status === "approved") {
  res.status(409).json({ error: "approved_request_cannot_be_deleted" })
}
// 否則連刪三張表：
await supabaseAdmin.from("request_attachments").delete()...
await supabaseAdmin.from("approval_steps").delete()...
await supabaseAdmin.from("leave_requests").delete()...
```

**保護判準錯了。** 現況保護的是「會不會影響帳」，不是「會不會有爭議」：

- `approved` 的請假單 → 擋住（因為有 ledger effect）
- `pending` / `rejected` / `cancelled` → **HR 可硬刪**，連同附件與簽核軌跡一起消失

**而被駁回的申請，恰恰是最可能產生爭議的那一種。**
情境：員工提請假單 → 主管駁回 → 日後爭議，員工主張「我有申請、公司不准」
→ 該筆 rejected 紀錄已被刪 → 證據滅失，且滅失的是對雇主不利時唯一的反證。

這是設計者視角（保護帳務完整性）而非法務視角（保護爭議證據）的結果。

順帶：程式刪了 `request_attachments` 索引列，但**未刪 Supabase Storage 內的

#### 「嚴禁系統刪除」在應用層擋不住——必須做在 DB 層

整個 API 走 `supabaseAdmin`（service_role key），而 **service_role 繞過所有
RLS**。因此：

- 寫 RLS policy 禁止 DELETE → **無效**，service_role 照刪
- 移除 endpoint → 只移除一條路徑，key 在手仍可直接下 DELETE
- 且本 repo 的 `packages/db/sql/*.sql` 共 17 支 RLS 檔，**grep 不到任何
  DELETE 相關 policy**，DB 層目前零保護

**唯一連 service_role 都擋得住的是 BEFORE DELETE trigger**（trigger 不受
RLS bypass 影響）：

```sql
CREATE FUNCTION forbid_delete() RETURNS trigger AS $$
BEGIN RAISE EXCEPTION 'deletion forbidden on %', TG_TABLE_NAME; END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER no_delete BEFORE DELETE ON leave_requests
  FOR EACH ROW EXECUTE FUNCTION forbid_delete();
```

> 此點與帳本待辦 #4（「RLS policy 只在 pglite 以 owner 身分驗過，等於未驗」）
> 是同一個主題：**owner / service_role 繞過 RLS**。本條正好說明
> RLS 不是防刪的正確工具。

**實作注意（會咬人）**：現有測試以 `.delete()` 清理資料
（`payroll-run.test.ts`、`ledger.test.ts`、`kpi.test.ts` 等多處）。
加上 trigger 後這些測試會全部失敗。需先決定清理策略
（獨立 schema / 專用清理角色 / 測試改用 soft-delete 後 truncate），
不能直接加 trigger 了事。

#### 保存年限：不要用單一數字，且起算點客戶沒講清楚

法定年限依文件類型而異：

| 文件 | 年限 | 法源 |
|---|---|---|
| 出勤紀錄 | 5 年 | 勞基法 §30 V |
| 工資清冊 | 5 年 | 勞基法 §23 II |
| 勞工名卡 | 自離職起 5 年 | 勞基法 §7 II |
| 會計憑證 | 5 年 | 商業會計法 §38 |
| 會計帳簿、財務報表 | 10 年 | 商業會計法 §38 |
| 請假單據 | 法無明定 | 實務比照出勤紀錄 |

客戶說的「7 年」可能來自會計端的較長年限。
※ 各年限請會計師／律師覆核，依硬約束不臆斷。

**關鍵：起算點不是「文件建立日」，是「請求權時效屆滿日」。**

工資（含加班費）請求權適用民法 §126 五年時效，自**各期工資給付日**起算；
退休金請求權 5 年（勞基法 §58）。一份 2026 年的請假單，若員工 2026 年離職，
爭議可能 2031 年才發生。

**對規章版本更關鍵**：某一版規章要保留到
**「最後一位受該版規範的員工」請求權時效屆滿**，
而非「該版失效後 5 年」——因為爭議時要證明的是「當時適用哪一版」。

→ **保存期限應掛「最後適用日 + N 年」，不是「建立日 + N 年」。**
起算點取錯會提早刪掉關鍵證據。

**建議：根本不做自動清除機制。** 客戶說「嚴禁系統刪除」，那就不要寫 purge。
保存期限僅用於標示「可歸檔／可降冷儲存」，不觸發刪除。
儲存成本遠低於證據滅失的代價。

#### 版本模型

客戶講的「第一版、第二版」是**人類可讀版號**，與內部版本鏈是兩件事：

- `version_no` int — 給人看的版號
- `effective_from` / `effective_to` — 該版適用期間
- `supersedes` / `superseded_by` — 版本鏈
- `content_hash` — 證明內容未被替換
- `change_type` — **`'amendment'`（增修）vs `'annual_rollover'`（跨年度）**

最後一項對應客戶原文「當條款**跨年度**或有**增修**時」——**兩種觸發條件**。
跨年度意味著即使條款一字未改也要進版（年度特休、年度福利額度這類條款，
適用年度不同即為不同版本）。兩者必須能分開記，否則「今年與去年相同」
這件事本身無法證明。

#### 一致性問題：系統對「不可變資料」沒有統一策略

`payslips` 已有 `status='finalized'` 鎖定 + `version` 欄位遞增；
`announcements` 兩者皆無，`PATCH` 直接就地覆寫。
建議把「鎖定後不可改、只能發新版」做成跨表一致的 pattern，而非逐表各做各的。

### 模組二第 3 條（2026-09-11）

> 新人簽名補簽紀錄：新進同仁需於現行生效公告文件之後續欄位進行補簽並
> 更新掃描檔[13]

**處置：照做。但「更新掃描檔」四個字若照字面實作，會推翻第 2 條。**

#### 核心：兩條版本軸不能混在一起

**新人補簽不會讓規章「進版」。** 這條最容易做錯的地方就在這裡：

| 軸 | 觸發條件 | 例 |
|---|---|---|
| **內容版本** | 條款增修 / 跨年度（模組二第 2 條的 `change_type`） | 工作規則第一版 → 第二版 |
| **簽署快照** | 有人補簽 | 同一版規章的第 3 份掃描檔 |

若把兩者合為一軸：每來一個新人，工作規則就「進版」一次——內容一字未改
卻變成第 17 版，而真正的條款修訂被淹沒在補簽噪音裡。
勞檢或訴訟時「請提出當時生效的工作規則第幾版」會答不出來。

→ 兩張表：`announcement_versions`（內容版本鏈，第 2 條）與
`announcement_signature_sheets`（掃描檔快照，外鍵指向前者）。
補簽產生新的 signature_sheet，**不動 version**。

#### 「更新掃描檔」＝覆蓋，與第 2 條「嚴禁刪除」直接衝突

每次補簽覆蓋一次掃描檔，會失去「某時點誰已簽」的時間切片；
紙本若毀損或某個簽名被遮住，舊掃描檔已不存在，無從還原。

→ **掃描檔要加版，不是取代。** 舊版全部保留（同第 2 條的保存原則）。
沿用 `request_attachments` 的私有 bucket 模式，加 `content_hash` 與版序。

#### 紙本補簽的時間陷阱

「於現行生效公告文件之**後續欄位**進行補簽」＝在同一張傳閱單的下一格簽。

**但傳閱單頂上是公告日期**（例如 2026-01-15），新人 2026-09-01 補簽時，
那張紙不記錄他何時簽的。爭議時看起來像他一月就在場，或日期根本說不清。

而模組二第 1 條已指出：不利益變更需證明**每個人何時同意**。
紙本補簽剛好把這個資訊弄丟。

→ 結構化紀錄帶自己的 `signed_at`，掃描檔只是佐證。
（即第 1 條提的 `announcement_acknowledgements.signed_at`。）

#### ⚠️ 同一張紙上的兩種簽名，法律意義不同（客戶未必想到）

| 誰簽 | 法律性質 |
|---|---|
| 在職員工簽**不利益變更** | **同意變更**既有勞動條件（需個別同意，不同意者不生效力） |
| 新人到職**補簽** | **接受既有勞動條件**——對他而言不存在「變更」，這是聘僱條件的一部分 |

同一份文件、同一張傳閱單，兩種簽名的舉證作用完全不同。

**實務影響**：日後盤點「這次不利益變更有多少人同意」時，新人的補簽
**既不該進分母也不該進分子**——他們不是「同意變更」的對象。
混在一起會讓同意率失真，而那個比率正是不利益變更是否生效的關鍵事實。

→ `announcement_acknowledgements.kind`：
`'consent_to_change'`（同意變更）／`'accept_on_hire'`（到職接受）。

#### 「現行生效公告文件」是複數——這是入職清單，不是單一動作

新人要簽的是**所有現行生效的規章**，不是一份。

現況：`packages/db/src/schema/onboardings.ts` 僅有
name / deptId / managerEmpId / employmentType / identityType / region /
reportDate / status / employeeId。**無 checklist、無文件簽署概念**
（grep `checklist` / `sign` 皆空）。

掛接點明確：`POST /onboardings/:id/complete`（`routes/onboardings.ts:254`，
把 pending 轉成正式 employees 列）時自動生成待簽清單：

```
所有 effective_from <= today
  AND (effective_to IS NULL OR effective_to > today)
  AND requires_signature 的公告版本
```

模組二第 1 條的「**誰還沒簽**」清單視圖自然涵蓋新人，不需另做。

#### 順帶：離職者的簽名會長期留在掃描檔內

傳閱單上有離職員工的姓名與簽名，掃描檔保存 5~7 年會一直帶著這些個資。
保存本身正確（爭議需要），但個資法上需有明確的保存目的與期限，
並納入個資清冊。非本條阻塞項，列為提醒。

##### 1. `audit_logs`（移植缺口 #1）— 雙來源設計

| 來源 | 保證 | 限制 |
|---|---|---|
| DB trigger（`sql/0019`） | 擋不掉、繞不過，**「什麼被改了」不會漏** | DB 不知道應用層操作者是誰（API 全走 service_role，`request.jwt.claims` 只有服務身分）→ `actor_emp_id` 為 null，只記 `db_user` |
| 應用層（`services/audit.ts`） | 補上 `actor_emp_id` 與 `context` | 可被繞過（漏呼叫、直接下 SQL） |

兩者互補，查核時以 `(table_name, record_id)` 拼起來看。
`writeAuditLog()` **永不 throw**——稽核寫入失敗不該讓業務操作失敗

##### 2. `announcement_versions` — 內容版本鏈

`PATCH /announcements/:id` **不再就地覆寫，改發新版**：
新版 `version_no + 1`、舊版補上 `effective_to`、本表的
title/body/audience 作為現行版的去正規化快取同步更新

`change_type` 對應客戶原文「當條款**跨年度**或有**增修**時」兩種觸發：
`amendment` / `annual_rollover`。**跨年度時內容三欄可全部省略**——條款一字
未改也要進版，否則「今年與去年相同」這件事本身無法證明。

`requires_signature` 未指定時沿用前一版：那是文件的性質，不會因為改一行字
就消失。`is_adverse_change` 則每次明示（不利益變更是逐次判斷的事實）。

`content_hash`（sha256 of title+body+audience）證明某一版文字未被事後替換。

`announcements.current_version_id` 刻意無 FK：與
`announcement_versions.announcement_id` 互為環狀參照，加 FK 需 deferrable
constraint，收益不值得那個複雜度。

##### 3. `announcement_signature_sheets` — 掃描檔快照

**處置：照做。但「油錢補貼」四個字會決定這條是合規還是漏報薪資所得。**

#### 現況：引擎想對了，但沒有資料來源

```ts
// packages/rules/src/payroll-engine.ts:67-69
rules: RuleConfig,
/** 本期核准的員工代墊支出合計 (加項)。預設 0。 */
expenses = 0,

// :206-208
// 代墊支出是「代收代付」,不是薪資所得 → 不進 gross,直接加在實發。

const net = round(gross - totalDeductions + expensesTotal);
```

**引擎的處理完全正確**——實報實銷的代墊款不是所得，不進 gross、不影響
扣繳與投保薪資，直接加在實發。

但：

|---|---|
| 報銷資料表 | ❌ **完全不存在**（全域 grep `expense` / `reimburse` / `報銷` / `代墊` / `差旅` 在 db schema 與 api 皆無） |
| 呼叫端傳入 | ❌ `routes/payroll.ts:273` 只傳三個參數，**第四個 `expenses` 從未傳過** → 恆為 0 |

#### ⚠️ 本條最關鍵的設計決定：「補貼」不是「報銷」

客戶原文列的是「夜間計程車、捷運、公車及**油錢補貼**」。前三項是實支實付，
**「補貼」通常是定額給付**——兩者稅務性質完全相反：

| 性質 | 所得稅 | 勞健保投保薪資 | 引擎路徑 |
|---|---|---|---|
| **實報實銷**（有憑證、金額＝實際支出） | 非所得，不課稅 | 不計入 | `expenses` 加項，不進 gross |
| **定額補貼**（每月固定 X 元，不論實花） | **屬薪資所得**（所得稅法 §14 第 1 類含各種補助費） | **應計入** | 必須進 gross |

**若把定額補貼丟進 `expenses`：不課稅 ＋ 不計保 ＝ 漏報薪資所得 ＋ 高薪低報。**

這與 2026-08-26 找到的「勞健保費 0 元」屬同一類風險（少計投保薪資），
但成因相反：那次是欄位沒帶到，這次會是**性質判斷錯誤**。

→ **每一筆報銷必須帶 `nature` 旗標**：`'reimbursement'`（走 expenses 加項）
／`'allowance'`（進 gross、影響投保薪資）。這是本條的核心欄位，不是選配。

※ 具體認定標準與免稅限額（差旅費部分另有營所稅查核準則 §74 的規定）
請會計師覆核，依硬約束不臆斷。

#### 「不需逐筆事前審核」可以，「不要憑證」不行

客戶要的是流程效率（不要每張計程車收據跑一次簽核），這合理且該做。但：

- 稅上要主張「非所得的代墊費用」，需要憑證
- 營所稅要列費用，需要憑證
- **沒有憑證的給付，國稅局傾向認定為薪資**

→ **事前審核可省，憑證不可省。** 月結時管理者核的是「這批有沒有問題」，
系統的責任是把憑證收齊、異常標出來，讓那一次審得有意義
（沿用 `request_attachments` 的私有 bucket 模式）。

#### ⚠️ 「夜間計程車」是加班的旁證——這條與模組一第 1~3 條互相矛盾

**出勤紀錄顯示 18:00 下班，同一天卻有 23:30 的計程車報銷 —— 那是矛盾。**
勞檢與訴訟中，報銷單據會被用來證明實際工時。

→ 若模組一第 1~3 條真的實作了「超時打卡轉 C 單」，**模組三的交通費報銷會
把藏起來的加班暴露出來**。藏工時但報車錢，兩份紀錄自相矛盾，
**比不藏更糟**——矛盾本身就是造假故意的證據。

客戶自己要的兩個模組會互相打臉。這是從第三個角度再次證明第 1~3 條的
拒絕是對的。

**反過來可以當賣點**：做「報銷 × 出勤交叉檢核」——夜間交通費報銷但當日
無對應加班紀錄 → 標示異常。對客戶是提醒工時漏記（該補），對法遵是自我檢查。

#### 月結的兩個實務細節

1. **發生日與歸屬期要分開**：`incurred_on`（實際發生）vs `period`（結算歸屬）。
   遲交的收據（上月的這月才交）掛當期，但保留原發生日——否則跨月費用的
   帳務歸屬與出勤交叉檢核都會錯。
2. **期間鎖定，且順序要對**：月結核銷後該期應鎖定（比照 payslips 的
   `finalized`）。**若報銷隨薪資發放，必須在 `POST /payroll/run` 之前鎖定**，
   否則核銷後才補的單不會進當期薪資。

#### 順帶：油錢補貼 ＋ 自用車 → 職災認定

**知悉並同意其以自用車執行職務**——報銷紀錄就是那個「知悉」的證據，
會影響職災認定與雇主責任範圍。非本條阻塞項，列為提醒。

##### 核心：`nature` 一分為二，兩條路徑到底

客戶原文列「夜間計程車、捷運、公車及**油錢補貼**」，前三項實支實付，
「補貼」通常是定額給付——兩者稅務性質相反，系統全程不可混算：

| `nature` | 稅務 | 投保薪資 | 引擎路徑 |
|---|---|---|---|
| `reimbursement` | 非所得 | 不計入 | `computePayslip` 的 `expenses` → **不進 gross**，只加在實發 |
| `allowance` | **薪資所得** | **應計入** | `computePayslip` 的 `allowances` → **進 gross** |

`nature` 在三個地方各存一份，各有理由：
- `expense_categories.nature` — 類別預設值
- `expense_claims.nature` — **凍結在單上**。類別的預設性質日後可能調整，
  但已送出的單必須保留當時的稅務認定，否則無從追溯。HR 覆寫進 audit_logs。
- `expense_settlements` 的 `reimbursement_total` / `allowance_total` 分開存

##### 薪資引擎：新增 `allowances` 參數（rules 49 → 56）

```ts
computePayslip(days, salary, rules, expenses = 0, allowances = 0)
gross = base + overtimePay + nightPay + attendanceBonus + allowances
net   = gross − totalDeductions + expenses
```

- 「同額的補貼與代墊，**gross 不同但實發相同**」——證明兩條路徑真的分開

**引擎不會因補貼而自動調整保費**：投保薪資是另行申報的級距，不是從當月

### 模組三第 2 條（2026-09-12）

> 專案出差事先審核：跨縣市（如前往高雄、花蓮）等長途專案出差，同仁需線上填寫
> 「出差申請表」，經老闆簽核同意後方可成立並放款[15]

**處置：照做。申請與簽核**已存在**，缺的是「放款」那一段與兩條軌道的連結。**

#### 與第 1 條合起來看：這是兩軌政策

| 軌道 | 事前審核 | 觸發條件 |
|---|---|---|
| 日常常態（第 1 條） | **不需要** | 夜間計程車、捷運、公車、油錢 |
| 長途出差（第 2 條） | **必須，且要老闆簽** | 跨縣市 |

小額例行的放行、大額長途的把關——這是合理的政策，不是自相矛盾。

**但系統必須知道一筆報銷走哪條軌道。** 否則員工把出差費用拆成「日常」報銷
就能繞過事前審核，**第 2 條即形同虛設**。這是分開做兩條規則一定會漏掉的接點。

→ `expense_categories` 需加「是否須綁已核准出差單」的旗標；走出差軌的類別，
`expense_claims` 必須帶 `trip_request_id` 且該單為 `approved`。

#### 現況：申請與簽核已完整

| 需求 | 現況 |
|---|---|
| 線上出差申請表 | ✅ `requests.ts` 的 `kind='business_trip'`，帶 `tripType`（公出／出差）、`location`、`remark`、`agentName`、多段日期 |
| 經老闆簽核 | ✅ `approval_flows.approverEmpIds` 是**有序**陣列——把老闆的 empId 設為唯一簽核人即可，不需改程式 |
| 核准後「成立」 | ✅ 最終核准即 `status='approved'` |
| **核准後「放款」** | ❌ **完全沒有**。`applyApprovalEffects` 只處理 `leave` / `ot`，`business_trip` 核准後不產生任何金流 |
| 跨縣市／長途判定 | ❌ `location` 是自由文字，無任何分級 |

#### ⚠️ 待確認（阻塞建模）：「放款」是預支還是實報？

原文「方可成立並**放款**」有兩種讀法，**資料模型完全不同**：

1. **事前預支**（出差前先撥款）
   → 要有預支金額、回程後核銷沖抵（多退少補）、未核銷預支於離職時扣回
   → **這正好是 `advance` 的第一個真實資料來源**：引擎的
   `SalaryStructure.advance` 與 `PayslipBreakdown.advance` 欄位早已存在，
   但 `payroll.ts:74` 註解明寫「advance 仍無來源；要支援需先加 migration」，
   帳本待辦 #3 也記著 `salary_structures` 缺預支欄位。
2. **核准後才受理報銷**（回程實報實銷，未核准的出差不受理）
   → 只需把 `expense_claims` 綁到已核准的出差單，不涉及預支

字面像 (1)，實務上 (2) 更常見。**必須問清楚**。

#### ⚠️ 出差期間算不算工時（客戶必然沒想到，且是勞檢重點）

- 出差期間的**工作時間**是工時。
- **往返交通時間**：勞動部見解，非受雇主指揮監督者原則上不計入工時；
  但途中仍須處理公務（開會、接電話、搬運設備）則屬工時。
- 跨縣市長途常是「早上六點出門、晚上十點到家」。若出勤只記 9–18，
  又是模組一第 1~3 條那個矛盾。

**而且出差申請單本身就是書面證據**：單上寫明地點與日期＝「該員當日在高雄」。
若同日的 `punch_records` 顯示他在台北的 GPS 圍欄內打卡——
**公司自己的兩份紀錄互相矛盾**。

`punch_records` 已有 `lat` / `lng`，此交叉檢核做得出來。
與第 1 條的「報銷 × 出勤」同類，但更直接。

#### 差旅費的稅務比日常報銷多一層

營所稅查核準則 §74（旅費）：出差旅費須有**出差報告單**與證明文件；
膳宿雜費在財政部核定標準內免檢附憑證，超過部分須憑證。
員工差旅費在合理範圍內非所得，**日支超過標準的部分屬員工所得**。
※ 標準與認定請會計師覆核。

→ 第 1 條的 `nature` 二分（reimbursement / allowance）在出差這裡**不夠**：
還有**日支（per diem）**這第三種——標準內非所得、超標部分是所得。
客戶未提日支，列為待確認，不自行加建。

**順手可得的價值**：出差申請單已有 location / start_at / end_at / reason /
remark，補上回程的「出差報告」欄位，就同時滿足查核準則要求的出差報告單。
客戶沒要求，但幾乎不用多做。

#### ⚠️ 「老闆簽核」的單點風險——這會讓制度自己失效

若所有出差都要老闆本人簽，老闆出國或忙碌時流程即卡住，實務上會演變成
**「先去再補簽」**——事前審核失去意義，且補簽日期是假的
（同模組二第 3 條的簽署日問題）。

`approval_flows` 目前是固定有序陣列，**無代理人、無逾時升級、無門檻分流**。

建議至少做**門檻分流**：短程小額由主管簽、長程大額才到老闆。
這保護的是制度本身的有效性，不是圖方便。門檻應為可設定參數。

#### 跨縣市判定：用下拉，不要猜文字

`location` 是自由文字，字串比對縣市不可靠，GPS 距離則過度設計。
建議在申請單加「出差範圍」下拉（市內／跨縣市／海外），由填報者選。
且「跨縣市」的門檻應可設定——台北公司去桃園與高雄公司去桃園，性質不同。

#### 建議動工範圍（待「放款」語意確認後）

1. `leave_requests` 加出差欄位：`trip_scope`（市內／跨縣市／海外）、
   `estimated_cost`、`advance_amount`、`trip_report`（回程填）
2. `expense_categories` 加 `requires_trip_approval`；
   `expense_claims` 加 `trip_request_id`，走出差軌者必填且須為 approved
3. `applyApprovalEffects` 補 `business_trip` 分支：核准後依 (1)/(2) 的選擇
   產生預支紀錄或解鎖報銷
4. 若走預支：補 `salary_structures` 預支欄位（帳本待辦 #3 一併處理），
   把 `advance` 接上薪資引擎
5. 出差 × 打卡地點交叉檢核（比照第 1 條的報銷 × 出勤）

**使用者更正**：先答「放款是實報」，隨即更正為

##### ⚠️ 本輪最重要的發現：會重複給付的陷阱

出差採「先撥預支、回程沖抵」，而回程的報銷單也寫進 `expense_claims`。
若這些單同時走月結的一般 `expenses` 加項：

```
員工預支 5,000 → 出差實花 6,000 → 報 6,000 的 expense_claims
月結：expenses 6,000 加在實發
但員工已先拿 5,000
→ 公司總共付 11,000，多付 5,000
```

**修正**：`payroll.ts` 的一般報銷查詢加 `.is("trip_request_id", null)`
排除綁出差單者；出差那一軌**只結差額**（`trip_advances.balance`）。

這個錯誤如果沒在設計階段抓出來，會變成「每一趟出差都多付一次預支金額」，
而且因為兩邊數字各自看起來都合理，對帳時極難發現。

##### `trip_advances` — 獨立的金流表

| 狀態 | 意義 |
|---|---|
| `requested` | 出差單最終核准時自動開單（`applyApprovalEffects` 的 business_trip 分支），金額取自 `leave_requests.advance_requested`。**尚未撥款** |
| `paid` | HR 撥款，記 `paidAt` / `paidByEmpId` / `payoutChannel`（cash / transfer）。**此時起是公司對該員的債權** |
| `settled` | 回程核銷：綁定的報銷單合計為 `actualTotal`，`balance = actualTotal − amount`。正＝公司補給員工，負＝員工應退 |
| `cancelled` | 出差取消且款項已收回 |

**核准與撥款刻意分開**：只有分開才看得出「已核准但還沒拿到錢」與
「已撥款但還沒核銷」是兩種不同狀態，後者才是債權。
`GET /trip-advances/outstanding` 回傳後者並附 `daysOutstanding`——
那是離職結算要扣回的依據，也是「回來很久卻沒交單」的催辦清單。

**`balance` 於核銷當下凍結存下**（而非日後由 actualTotal − amount 現算）：
綁定的報銷單若之後有異動，核銷當下的結論不該跟著變。

**為何獨立成表而非在 leave_requests 加欄位**：這是金流，要記誰撥的、何時撥、
什麼管道、怎麼沖抵。散在請假單上既難稽核，也查不出「誰還有未核銷的預支」。
獨立表也讓硬約束「經手金額的表一律掛 audit trigger」有明確掛載對象
（已納入 sql/0018 禁刪與 sql/0019 稽核）。

##### 兩軌政策的閘門（第 1、2 條的接點）

- `expense_categories.requires_trip_approval`（預設 false ＝日常軌）
- `expense_claims.trip_request_id`

`POST /expenses` 對 `requires_trip_approval=true` 的類別強制要求
`tripRequestId`，且驗證該單為**本人、已核准的 business_trip**。
四種失敗情形（不存在／非出差單／非本人／未核准）**一律回同一個錯誤**，
免得成為探測他人單號的管道。

**沒有這道閘門，出差費用可以拆成「日常」報銷繞過事前審核，第 2 條形同虛設。**

##### 修正帳本待辦 #3 的一半：`advance` 不該在 `salary_structures`

待辦 #3 原記「`salary_structures` 缺勞退自提率、預支欄位 → `advance` 無資料來源」。

**預支沖抵是逐期發生的事件，不是員工的固定薪資結構。** 放在 `salary_structures`
會變成每期人工改、改了沒有歷史。正確來源是逐期彙總的預支沖抵紀錄——
與本輪稍早做的 `expenses` / `allowances` 同一個模式。

實作：`toSalaryStructure(row, nhiDependents, advance)` 第三個參數由
`trip_advances`（settled / balance_handling='payroll' / recovery_period=本期）
彙總而來。
- `balance > 0` → 併入 `expenses` 加項（公司補給員工，非所得）
- `balance < 0` → 併入 `advance` 扣項（從薪資扣回）

→ 待辦 #3 剩下的是**勞退自提率**（`pensionVoluntaryRate`），那個確實是薪資結構
的屬性，仍需 `salary_structures` 加欄位。

#### 這條與第 2 條的關係

| | 模組三第 2 條（出差預支） | 模組三第 3 條（零用金預支） |

| 觸發 | 跨縣市長途出差 | 單次費用逾 5,000 |
| 授權 | 老闆簽核出差單 | 主管／老闆同意 |
| 撥款 | 已做（`trip_advances`） | 「由會計發放現金」 |

差別只在「誰授權」與「憑什麼授權」。

#### 建議：把 `trip_advances` 一般化成 `advances`

**理由不是省工，是離職結算。**

未核銷預支是離職時扣回的依據。若出差預支與零用金預支分成兩張表，
**離職結算必須查兩個地方——一定有人漏查其中一張，而漏查的那筆就是收不回來的錢。**
同理，「這個人身上還有多少公司的錢」這個問題不該有兩個答案。

改動：
1. `trip_advances` → `advances`，加 `kind`（`'trip'` / `'petty_cash'`）
2. `trip_request_id` 改為**可空**（零用金沒有出差單）
3. `expense_claims` 加 `advance_id` 作為**沖抵的連結**
   —— 目前是靠 `trip_request_id` 反推，零用金沒有出差單可反推。
   兩欄各有職責，不重複：
   - `trip_request_id` = 這筆費用屬於哪趟出差（**兩軌閘門**＋歸屬）
   - `advance_id` = 這筆費用用哪筆預支的錢付的（**沖抵**）
4. 零用金申請走既有的申請簽核管線：`KINDS` 加 `petty_cash`，
   核准時 `applyApprovalEffects` 開出 `kind='petty_cash'` 的預支
   —— 與出差完全一致，不必另建簽核機制。

> ⚠️ 若 `docs/套用-2026-09-12-增量.sql`（建 `trip_advances`）已套用到 Supabase，
> 改名需要一支 `ALTER TABLE ... RENAME` 的 migration；尚未套用則直接改即可。
> 兩種情況都不難，但要先確認。

#### ⚠️ 待確認：5,000 是門檻還是硬性下限？

原文「單次費用**超過** 5,000 元…同仁**可**線上提出」——讀起來是
「什麼情況適合申請」，不是「低於 5,000 不准申請」。
**做成硬擋是過度解讀**（有人可能正當需要 4,000 的預支）。

建議：金額門檻做成**可設定參數**（預設 5,000），UI 提示，
低於門檻的申請**標示但不擋**，由簽核者判斷。

同時要有下限的另一個理由：若任何人都能為任何理由申請預支，
零用金會變成變相的薪資借貸方案。門檻是把它框在原本的用途裡。

#### ⚠️ 「由會計發放現金」——系統沒有會計角色

`employees.role` 目前只有 `employee` / `hr_admin` / `platform_admin`
（`middleware/role.ts`），所有金流操作都掛在 `requireHrAdmin` 之下。

**現金發放與薪資核算是不該由同一個人做的兩件事**（職務分立）。
而 `docs/01-需求評估與待確認.md` 早已指出「權限分層過粗：會計要匯款必須
知道獎金金額，但不需知道趴數／計算基礎 → 拆成兩種權限」——
**本條再次撞上同一個問題**，而且這次是客戶自己講出「會計」這個角色。

→ 建議新增 `accounting` 角色，現金發放權給它而非 `hr_admin`。
這不是新需求，是把已經記了三個月的缺口補上。

#### ⚠️ 現金發放缺兩件東西

`advances` 已記 `payoutChannel`（cash / transfer）與撥款人、時間，但缺：

1. **領款簽收** —— 誰確認「錢確實到本人手上」。現金是最容易起爭議的管道，
   撥款人單方面的紀錄不足以自證。比照模組二第 1 條的簽收模型即可。
2. **零用金箱的餘額** —— 客戶說「由會計發放現金」，那筆現金從哪來？
   誰管餘額？何時補充？系統目前只記「撥了多少給誰」，
   **沒記「箱子裡還剩多少」**。完整的零用金制度（imprest）需要進出帳。
   → 客戶未明示，列為**待確認**，不自行加建。

#### 稅務：預支是借款，不是所得——但有前提

員工預支在沖抵之前性質是**借款**，不課稅、不計入投保薪資。
但**長期不沖抵、實質變成變相薪資**，則可能被認定為所得。

`GET /trip-advances/outstanding` 的 `daysOutstanding` 已讓這件事可見；
一般化後應沿用，並考慮把逾期門檻做成可設定參數。

#### 沿用第 2 條已指出的缺口

**金額門檻分流**（小額主管簽、大額老闆簽）目前做不到：
`approval_flows` 是 per-kind 的固定有序陣列，無門檻、無代理人、無逾時升級。
本條的「主管**/**老闆同意」正是需要門檻分流的情境——
5,000 的計程車費與 50,000 的預支，不該是同一個人簽。

這與模組三第 2 條「老闆簽核的單點風險」是同一個缺口，兩條都指向它。

## 模組四：專案行政與請款追蹤（Project Management & Billing）

### 模組四第 1 條（2026-09-12）

> 專案申請單編號與子目錄：每筆專案需建立唯一編號之「專案申請單」[17]；
> 鑑於專案請款期可長達 2～4 年，需提供子目錄架構記錄多期請款進度

**處置：照做。但這條是帳本「移植五個缺口」裡**三個**的共同入口，
動工前要先決定要不要一次做齊，否則之後必然回頭改結構。**

#### 為何是三個缺口的入口

帳本 2026-08-26 列的五個缺口中：

| 缺口 | 與本條的關係 |
|---|---|
| 分期請款 / 發票 / 入帳（區塊 F） | **就是本條的「多期請款進度」** |
| 合約版本 + 印花稅（區塊 E） | 「專案申請單」對應一份承攬合約；印花稅（承攬契據千分之一）掛在這裡 |
| 集團代收代付（區塊 L） | docs/01 第六節的邊界表：**簽約公司 ≠ 開票公司**時要標記 `requires_review`。**開票一旦建模，那張表就必須同時實作**，否則之後要回頭改開票的資料結構 |

且帳本 2026-08-24 的決策已經寫過：
**「專案/請款/獎金是同一組資料的三個投影，切碎做會重工」。**
本條就是那組資料的入口。

#### 現況：三個基本欄位都不在

| 需求 | 現況 |
|---|---|
| 唯一編號 | ⚠️ `projects.code` **存在，但可空且無 unique index**。租戶內不保證唯一 |
| 合約總額 | ❌ **不存在**。`projects` 只有 `bonusPool`（分潤池），沒有合約金額 |
| 客戶／業主 | ❌ **不存在**。沒有客戶表，請款要開給誰無處可記 |
| 多期請款 | ❌ **完全不存在**（`invoice` / `billing` / `請款` / `收款` 全域 grep 為空） |
| 子目錄（檔案） | ⚠️ `project_documents` 存在，但**是平的**——只綁 `projectId`，無期別層級 |

**沒有合約總額，「多期請款進度」沒有分母**——算不出完成百分比，
也算不出還剩多少沒請。這是最先要補的欄位。

#### 「唯一編號」必須做在 DB 層

`projects.code` 目前無 unique index。**只靠應用層檢查會在併發時破功**：
兩個人同時建專案，各自查都說沒重複，然後都寫進去。
需 `uniqueIndex(tenant_id, code)`，比照既有的 `leave_types` / `expense_categories`。

**待確認：編碼規則。** 年度-類別-流水號（如 `A2026-001`）？
流水號跨年重置還是連續？是否人工指定或系統產生？
2~4 年的專案會跨年，編號規則若含年度就要定義「以哪一年為準」。

#### 「子目錄」是兩件事，客戶原文指向前者

「子目錄架構記錄多期請款**進度**」——「進度」二字指向**資料結構**，不是檔案夾。
但兩種都合理，而且大概都要：

1. **分期請款的層級**：專案 → 第 1 期 / 第 2 期 / 第 3 期（資料）
2. **每期的文件**：請款單、發票、驗收單分期存放（檔案）

建議：建 `project_billings`（期別），`project_documents` 加**可空的** `billing_id`
——專案層級的文件（合約、申請單）掛 project，期別文件掛 billing。
一個可空外鍵就同時支援兩層，不必另建表。

#### ⚠️ 請款 ≠ 開票 ≠ 收款：三個事件，不是一個狀態欄位

這是本模組最容易做錯的地方。三者**時間不同、金額也可能不同**：

- **請款**：送請款單給客戶
- **開票**：開立統一發票
- **收款**：錢真的進來（可能部分收、可能折讓、可能扣保留款）

做成單一 `status` 欄位必然失真——「已請款」無法表達「開了票但只收到七成」。
三個事件各自要有日期與金額。

**開票時點有稅務意義**：依「營業人開立銷售憑證時限表」，工程業通常於
「按約定應收價款時」開立發票，開晚了會被罰。
→ 系統若能標示「**已請款但逾期未開票**」，那是實際可用的價值，成本也低。
※ 時限表的適用類別請會計師確認。

#### 2～4 年 → 三個連鎖問題（docs/01 早已指出）

1. **營收認列**：長期工程合約用完工百分比法或全部完工法，是會計師的判斷。
   **系統不做認列判斷，但必須提供數字**：合約總額、累計已請款、累計已收款、
   完成百分比。沒有這些，會計師無從認列。
2. **獎金結轉**：docs/01 模組 5「獎金隨每期收回的 20% 款項同比例分期拆發」
   ——**請款期數與獎金發放是綁定的**。所以 `project_billings` 一建立，
   獎金就該掛上去，不能之後再接（接不上，會變成兩套期別）。
3. **人員異動**：docs/01 記 `project_members.left_at`——2~4 年的專案，
   中途一定有人離職，未發完的分期獎金歸屬要有答案。

#### ⚠️ 待確認：保留款（retention）

工程業常見合約總額的 5~10% 保留至驗收後才付。
這使「已請款總額 ≠ 應收總額」，且保留款的收回往往在結案後很久。

客戶未提，但 2~4 年的工程案**幾乎一定有**。若模型不預留，
之後會出現「這筆錢請了卻收不到，系統顯示逾期」的假警報。

#### 建議動工範圍（待編碼規則與保留款確認後）

1. `projects`：`code` 加 `uniqueIndex(tenant_id, code)` 並改必填；
   加 `contractAmount`、`clientId`、`signedAt`、`startDate` / `endDate`
2. 新 `clients`（客戶／業主）：名稱、統編、聯絡人、地址（開票要用）
3. 新 `project_billings`（期別）：`projectId`、`periodNo`、`plannedAmount`、
   **三組事件**（`billedAt`/`billedAmount`、`invoicedAt`/`invoiceNo`/`invoicedAmount`、
   `receivedAt`/`receivedAmount`）、`retentionAmount`、`note`
   —— 開票欄位須同時帶 docs/01 第六節的「開票公司」與 `requires_review` 標記
4. `project_documents` 加可空的 `billingId`
5. 稽核：`projects` 已在 sql/0019 的全量稽核清單，新表一併納入；
   金流表（billings）納入 sql/0018 禁刪

#### 實作（2026-09-12）：編號格式先做

> 使用者裁示：**「編號格式先做，之後有特殊需求再改」**

只做編號這一件事。合約總額、`clients`、`project_billings`、保留款、
子目錄**都還沒做**，上面那份建議動工範圍原封不動留著。

**格式：`P{建立年}-{三位流水號}`，例如 `P2026-001`。**
要改格式只改 `apps/api/src/services/project-code.ts` 的三個常數與 `formatCode()`。

##### 編號的年度只能是「建立年」——這是被限制決定的，不是偏好

上面問過「編號含年度要定義以哪一年為準」。答案其實只有一個：

| 候選 | 為何不行 |
|---|---|
| 簽約年 | 立案時可能還沒簽約（先立案、後簽約），那時編不出號 |
| 開工年 | 更晚 |
| 完工年 | 2~4 年後才知道 |

編號在立案當下就要印在文件上，所以只能用立案當下已知的年度。
**2~4 年的專案到了第 4 年仍是當初的編號**，不隨時間改。

##### 因此：編號（識別碼）與歸屬年度（分析維度）必須是兩欄

- `projects.code` —— 識別碼。會印在合約、請款單、發票上，**建立後不可變更**。
- `projects.fiscal_year` —— 分析維度。報表、業績、獎金歸屬看這一欄，**可人工調整**。

12 月談成、1 月才立案的案子：編號是新年度，歸屬年度設回舊年度。

**不要用編號表達歸屬。** 混在一起就會出現「為了改歸屬而想改編號」的壓力，
而那個編號已經在客戶手上的合約上了。這是本條唯一真正的設計決定。

##### 不可變更 = 回 409，不是靜默忽略

`PATCH /projects/:id` 帶 `code` 回 `409 code_immutable`，且**整筆拒絕**
（同一請求裡的其他欄位也不寫入）。靜默忽略會讓人以為改成功了，
等到對帳才發現合約上的號跟系統裡的不同。
前端的 `updateProject()` 型別參數裡直接沒有 `code`，編譯期就擋一層。

##### 併發：讓 DB 當最後防線

`MAX(seq)+1` 在兩人同時建案時會拿到同一個號——這正是上面說的
「各自查都說沒重複、然後都寫進去」。所以：

- `uniqueIndex(tenant_id, code)` 是**唯一的保證**
- 應用層碰到 `23505` 就重算重試，最多 5 次，用完回 `503 code_generation_failed`
- 不用 `SELECT ... FOR UPDATE`、不用 advisory lock——搶鎖是把 DB 的工作搬到應用層

##### 人工指定編號（匯入舊案）

`code` 留空＝系統產號；填了＝人工指定，撞號回 `409 code_taken`，**不自動改號**
（人工指定就代表那個號有意義）。

且**人工編號不參與流水號計算**：只掃描符合本格式的既有編號。
否則一筆手打的 `ABC-999` 會把之後所有自動編號推到 1000。

##### `code` 維持可空（與上面「改必填」的建議不同）

既有專案沒有編號，改必填要先回填。Postgres 的 unique index 視 NULL 互不相等，
所以可空不影響唯一性。新建一律由 API 產號，實務上不會再有空值。
要收成必填等舊資料清乾淨再說——為了形式上的漂亮去改既有資料不划算。

### 模組四第 2 條（2026-09-12）

> 專案動態狀態註記：專案需設有狀態選單，包含「進行中」、「結案」、「已解約」等選項，
> 用以明確標示解約或暫停等特殊案情[19]

**處置：照做。但先講清楚——選單本來就存在，只是什麼都不做。**

#### 現況查證

```
projects.status  text NOT NULL DEFAULT 'active'
z.enum(["active", "archived"])                    // API
<option>進行中</option><option>已封存</option>      // UI
```

全庫 grep `archived` 只有 4 個位置：enum 定義、UI 兩個 option、前端型別。
**沒有任何地方讀它**——不篩選、不擋、不進報表。`GET /projects` 連 query param
都沒有，一律全撈。

而且專案是一座孤島：

| 可能該被狀態影響的 | 現況 |
|---|---|
| 請款 / 開票 / 收款 | ❌ 不存在（第 1 條記過） |
| 費用報銷綁專案 | ❌ `expense_claims` 無 `project_id` |
| 出差單綁專案 | ❌ `leave_requests` 無 `project_id` |
| 儀表板 / 報表 | ❌ 完全沒撈 projects |
| 成員、分潤、文件 | ✅ 存在，但都不看 status |

**所以今天沒有東西可以擋。** 這條做的是資料模型與 UI，行為要等
`project_billings` 出來才有對象。先說清楚，免得做完以為狀態會開始攔東西。

#### 判斷一：「已封存」不是案情，是可見性

客戶列的進行中／結案／已解約／暫停全是**案情**。`archived` 是「我還想不想
在列表看到它」。塞進同一個 enum，要封存一個已解約的案子就得把 `terminated`
覆寫成 `archived`，**「這案子是解約收場」就沒了**——而保留款收得到與收不到，
差別就在這裡。

→ 兩軸：`status`（案情）+ `archived_at`（可空時間戳）。
跟既有的 `deleted_at` 軟刪除同一個做法。

#### 判斷二：解約日 ≠ 輸入日

解約通知書上的日期可能是上個月，人資這週才進系統。而**解約日決定已完成
部分的請款範圍，也決定分期獎金的結算基準**（docs/01 模組 5：獎金隨收款
分期拆發，解約後收不到的款就沒有對應獎金）。

用 `updated_at` 當解約日，帳會錯。跟第 1 條的「請款 ≠ 開票 ≠ 收款」、
模組一的「出勤照實記」是同一個教訓：**事件日與輸入日是兩件事。**

→ `status_effective_on`（date，人填）與 `status_changed_at`（timestamp，系統）。

#### 判斷三：不擋轉移，只要求理由

結案後驗收不過要返工是真的，誤按也要能改回來，所以**任何轉移都合法**。

原本評估時說的是「轉入非進行中 + 從終止轉回」才要理由，實作時收斂成
**任何變更都要**：復工日對工期展延一樣重要，而且少一條分支就少一類 bug。

跟刪除申請單、補打卡必填理由同一個原則：擋不了人，但留得下痕跡。
完整轉移歷程 sql/0019 的稽核 trigger 已經有了，這裡補的是 audit_logs
給不了的「為什麼」。

**刻意不建 `project_status_history`**：跟 audit_logs 重複，而且形狀是錯的。
之後若要算「暫停了幾天」做工期展延，要的是 `project_suspensions(from, to)`
成對的表，不是一串轉移紀錄——那種表事後要自己配對首尾，很容易配錯。

#### 判斷四：狀態集合寫死，不做成設定表

客戶寫「包含…**等**選項」。做成租戶可自訂（像 `leave_types`）？**不做。**
狀態一旦可自訂，「哪些狀態算終止」就寫不死，之後請款的 gating 要跟著
可設定，複雜度整個炸開。彈性由 `status_reason` 自由填吸收。
真要第五種狀態，加一個 enum 值是一行；做成設定表是一個模組。

四值：`active` 進行中 / `suspended` 暫停 / `closed` 結案 / `terminated` 已解約。
客戶沒提「洽談中／未開工」，不自己加。

#### 規則集中在一個純函式

`resolveStatusPatch()` 把「使用者送來的狀態／封存意圖」換算成 DB 欄位，
所有規則都在裡面。路由只負責搬運——狀態規則會長，散在 handler 裡遲早有
一條路徑漏掉理由或漏掉時間戳。而且它不碰 DB，所以**本機測得到**（20 個測試）。

裡面兩條不明顯但重要的規則：

- **重複封存不覆寫 `archived_at`**——不該把原本的封存日洗掉
- **轉回進行中自動解除封存**——否則會變成「進行中但看不到」

以及一條防呆：**「進行中」的專案不能封存**。進行中與不想看到互相矛盾，
多半是誤按。暫停／結案／解約都可封存。

#### ⚠️ 舊資料轉換裡有一筆猜測

既有 `status='archived'` 的專案，**無從得知它是結案還是解約**——舊模型
沒記這件事。只能一律轉成 `closed` + `archived_at`，理由填「由舊制『已封存』
轉入，實際案情待人工確認」。`sql/0021` 檔末附了查詢把它們列出來補。

`CHECK (status IN (...))` 刻意放在 `sql/0021` 而不是 drizzle schema：
寫在 schema 裡，migration 會在既有 `archived` 資料上直接失敗；資料轉換
必須先跑，CHECK 才能加，而 drizzle migration 表達不了這個順序。
比照 sql/0018~0020：有順序相依的 DB 物件放那裡。

#### 自動封存（2026-09-12）

> 使用者裁示：**「先做四個，自動化」**

終止狀態滿 N 個月自動封存，N 可調（`project_settings.auto_archive_months`，

##### ⚠️ 暫停永遠不自動封存

只封存**終止狀態**（結案／已解約）。暫停不在此列——
**暫停的案子最需要被看見，收起來就真的忘了，而忘掉的暫停案就是沒人去追的爛尾。**

這是整個功能裡唯一可能被誤加的規則，所以在 schema、service、測試、UI tooltip
四個地方都寫了一遍。

##### ⚠️ 人工拉回來的要放過

有人特地解除封存（多半是在追尾款），排程當晚又把它收起來——**那個功能等於壞的**。

→ `projects.unarchived_at` 記下人工解除封存的時點，排程看這一欄放過該筆。
案情之後再變動（`status_changed_at` 更晚）才恢復自動：新的案情變動＝新的寬限期。

##### 起算日取「生效日」與「輸入時點」較晚者

補登一張三個月前的解約單，不該讓它當晚就消失——人總要有時間把尾款與驗收
文件收乾淨。反過來，預先登記一張下個月才生效的結案，也不該現在就封存。
取兩者較晚者同時滿足這兩件事。

兩個日期都沒有（舊資料）就不動：**不知道案子何時結束，就不要猜。**

##### 月份加法要夾住月底

`8/31 + 6 個月` 用 JS 的 `setMonth` 會滾成 `3/3`。`addMonths()` 夾到當月
最後一天（`2/28`，閏年 `2/29`）。差幾天在這裡無害，但這種函式一旦被別處
借用就會出事，所以一次寫對。

##### 為何不寫成一條 UPDATE ... WHERE

規則裡有「起算日取兩者較晚」與「人工拉回來的放過」，寫成 SQL 會是一串
看不懂的 `coalesce`/`greatest`，而且沒辦法測。撈回來用 TS 判斷——專案表
本來就不大（一租戶幾百筆），一天跑一次。

判斷全在純函式 `shouldAutoArchive()`，**本機測得到**（14 個測試）。

worker 是鐘，API 是手：`upsertJobScheduler("auto-archive-projects", "0 4 * * *", tz: Asia/Taipei)`
→ `POST /internal/projects/auto-archive`。排在出勤那兩支（02:00、03:00）之後。
一天一次就夠——門檻的單位是「月」，早幾小時晚幾小時沒有差別。

一租戶失敗不影響其他租戶（逐租戶 try/catch），冪等（已封存的撈不到）。

那張表，再寫一筆只是同一件事記兩次。`project_settings` 則需要補掛 trigger
（已在 `[5]` 段）。

### 模組四第 3 條（2026-09-12）

> 合約/報價單類型與印花稅追蹤：專案需註記搭配之文件類型為「合約」或「報價單」[20]；

**處置：照做，但這條沒辦法單獨做——它要的兩個欄位正是第 1 條列為「未做」的
合約金額與簽約日。做這條等於做 docs/02 的區塊 E。**

#### 現況：0 個檔案

帳本第 65 行早就記過「合約版本 + 印花稅追蹤 → 0 個檔案」。查證後確認：

| 需求 | 現況 |
|---|---|
| 文件類型（合約／報價單） | ❌ `project_documents` 只有 `fileName` / `contentType`，**無 `doc_type`** |
| 合約金額 | ❌ 不存在 |
| 簽約日 | ❌ 不存在 |
| 印花稅任何欄位 | ❌ 全庫 grep「印花 / stamp」只有 timestamp 與測試的 `stamp` 變數 |
| 合約版本鏈 / 追加減 | ❌ 不存在 |

`docs/設計參考/02-資料模型-v0.md` 區塊 E 早就設計過 `contracts` 表
（`doc_type` / `version` / `supersedes_id` / `amount` / `signed_status` /
`stamp_duty_*`），**一行都沒實作**。本條就是把那張表做出來。

#### 判斷一：「合約 or 報價單」是文件的屬性，不是專案的屬性

客戶原文「專案需註記搭配之文件類型」字面上像專案欄位。但報價單 → 得標 → 簽約
是同一個案子的**兩份文件**，兩份都要留：報價單是議價紀錄，之後有爭議要用。

存成專案單一欄位，簽約後就會把報價單那格覆寫掉。
→ 型別放在 `contracts` 列上；專案層級的「有沒有簽約」用**衍生**方式判斷
（存在 `doc_type='contract'` 且已簽的列），不另存旗標，避免兩份真相。

#### 判斷二：這個分類就是課稅開關，不是歸檔整齊

**報價單不是契據**（無雙方合意），不課印花稅；**承攬契據課千分之一**
（印花稅法 §5③、§7③）。客戶要這個分類**是為了報稅**，不是為了好找檔案。

這也回頭解釋了第 2 條為何不需要「洽談中」狀態：**階段是由文件表達的，不是狀態。**
只有報價單 = 還沒成案；有合約 = 成案。

#### 判斷三：⚠️ 「近 5 年」可能不夠，該是 7 年

稅捐稽徵法 §21：
- 已於規定期間申報且無詐術逃漏 → 核課期間 **5 年**
- **未於規定期間申報**，或以詐術逃漏 → 核課期間 **7 年**

印花稅是自行貼花。**若公司過去根本沒貼，那正是「未申報」的情形 → 追徵 7 年**，
且印花稅法 §23 罰鍰 5～15 倍。

**做 5 年清單，會正好漏掉最需要那份清單的情形。**
→ 保存／回溯期間做成參數，預設 7 年，報表可切 5／7。※ 請會計師確認。

#### 判斷四：⚠️ 銀錢收據 0.4%，是承攬契據的四倍，客戶沒提

印花稅法 §7①：銀錢收據按金額 **4‰**（承攬契據的四倍），
但「兼具營業發票性質之銀錢收據」除外。

工程業請款若開統一發票就不課；另開收據就要貼。
系統若只追合約會漏掉這一塊——而它的金額更大。
→ 至少要能標示「本期請款是開發票還是開收據」。這與第 1 條的「開票」欄位
是同一組資料，又一次印證「專案／請款／獎金是同一組資料的三個投影」。

#### 判斷五：⚠️ 誰貼花，取決於公司是承攬人還是定作人

印花稅法 §7③：承攬契據「**由承攬人**貼印花稅票」。

公司承包業主的案子 → 公司是承攬人 → 公司貼。
公司發包給下包 → 下包是承攬人 → **公司不貼**。

清單若不分這件事，會把下包合約也算進應納稅額，金額直接高估。
→ `contracts` 要有「我方角色」（承攬人／定作人）。

#### 判斷六：費率凍結在合約列上，不做 system_parameters

`docs/設計參考/專案硬約束-CLAUDE.md` 寫「法規參數一律進 `system_parameters` 表
帶生效日」，並明列印花稅千分之一。查證：**`system_parameters` 表不存在**，
既有法規參數（二代健保 2.11%、9B 門檻 20,000）是以「常數預設值 + 租戶設定覆寫」
處理（`packages/rules/src/tw-tax.ts`）。

但印花稅與薪資有一個關鍵差別：

- **薪資只算當期** → 預設值 + 租戶覆寫就夠
- **印花稅清單是回溯 5～7 年的** → 2021 年簽的約要用 2021 年的費率

→ 不建 `system_parameters`（為一個費率建一套子系統，與既有做法不一致），
改為**把當時適用的費率與試算金額凍結在 `contracts` 列上**。
比照 `advances.balance` 在核銷時凍結——同一個模式，這個 codebase 已經有了。

#### 判斷七：系統不報稅，系統提供數字

跟第 1 條的營收認列同一個原則。印花稅有數個判斷點：

- 是否屬承攬契據（勞務／買賣／混合型契約的歸類）
- 金額不確定的單價契約怎麼算（先按概算貼用、結算找補）
- **繕寫份數**（§13 同一憑證繕寫兩份以上，各份均應貼用）
- 是否已申請按期彙總繳納（免逐件貼花）
- §6 免稅憑證

系統該做的是**清單、試算、標示未貼花**，不是「算出應納稅額並宣稱正確」。
※ 以上稅務細節一律請會計師確認。

#### 判斷八：追加減帳最容易漏

追加工程款要補貼花。docs/02 的 `doc_type` 已含 `change_order`。
2～4 年的工程案一定有追加減，而追加的貼花是最常被忘的一筆——
**這是系統真正能幫上忙的地方**，比「列出主合約」有價值得多。

##### 課稅判定是兩個欄位的交集，不是一個

| docType | ourRole | 課不課 |
|---|---|---|
| `contract` 合約 | `contractor` 承攬人 | ✅ 千分之一 |
| `change_order` 追加減帳 | `contractor` | ✅ 追加款要補貼花 |
| `quotation` 報價單 | 任何 | ❌ 不是契據 |
| 任何 | `client` 定作人 | ❌ §7③ 由承攬人貼，發包出去的是下包在貼 |

再加一個人工覆寫 `stampDutyRequired`（auto / yes / no）吸收系統判不了的情形
（§6 免稅憑證、混合型契約的認定）。

##### 費率凍結在列上，重算也不抓當下設定

改金額會重算稅額（否則清單的數字跟合約上的金額對不起來），
但**重算用的是列上凍結的費率**，不是租戶當下的設定——本件適用的是簽約
當年度的費率。要改費率就明確帶 `stampDutyRate`。
補登舊約時直接指定當年度費率即可。有整合測試盯著這件事。

##### 「有沒有簽約」是衍生的，不另存旗標

`projects.hasSignedContract` 由「存在 `doc_type='contract'` 且有 `signedOn`
的未刪除列」推出。存旗標就會有兩份真相，而合約會改版、會作廢。
列表用一次 `in(project_id, ids)` 查完，不做 N+1。

##### 三個「算不出來」要分開計數，不能併進未貼花

清單真正的用途是「哪些該貼而還沒貼」。但有三種情形算不出稅額：

| 情形 | 處理 |
|---|---|
| 應貼花但**沒填金額** | `missingAmountCount` 獨立計數 |
| 應貼花但**沒填簽訂日** | `missingSignedOn` 獨立計數——它連區間查詢都進不去 |
| 減帳（負數） | 稅額回 0，**減帳不退稅** |

併進「未貼花 0 元」會看起來像沒事，而那正是要被追的一筆。

##### 不可改的欄位

`docType` 與 `ourRole` 經 `PATCH` 改不了——兩者決定課不課稅，改了等於
改變一個已經試算、可能已經貼花的結論。要改請作廢後重立一件。
（與第 1 條的 `code` 同一個原則，但這裡連 409 都不給，直接不在 schema 裡：
前端型別參數也拿掉了，編譯期就擋。）

##### 軟刪除，必填理由

`contracts` 進 `sql/0022` 的禁刪與稽核。**已貼花的合約被實體刪除，等於把
「這筆稅貼過了」的證據一起刪掉**，而核課期間最長 7 年，追徵時拿不出東西。

#### 現況：`docs/02` 區塊 F 設計過，零實作

#### ⚠️ 這條真正的內容是尾差，不是乘法

客戶說「嚴禁人工口算或 Excel 手動拉格」，痛點不是算不動，是**加總對不起來**：

```
合約 8,888,888，分 5 期每期 20%
  每期 8,888,888 × 20% = 1,777,777.6 → 四捨五入 1,777,778
  五期合計 = 8,888,890                ← 比合約多 2 元
```

**百分比加總剛好 100%，金額加總卻不等於合約金額。** 另一種：

```
合約 3,000,000「各三分之一」
  33.33% 打不出三分之一 → 999,900 × 3 = 2,999,700   ← 短收 300
  使用者為了湊數把末期改成 33.34%                    ← 這就是手動拉格
```

→ **最後一期不按百分比算，而是「合約總額 − 前面各期合計」。**
總和必然等於合約金額，使用者也不必為了湊數去改百分比。

尾差**單獨存一欄**（`residueApplied`）並在 UI 明示「含尾差 −2」——
悄悄併進金額裡，使用者會以為系統算錯。

#### 百分比永遠是「合約總額」的百分比，不是「剩餘金額」的

有人覆寫或實際請款金額不同時，兩種做法：

- **(a) 各期照原百分比算，差額掛末期** ← 採用
- (b) 未請款的期別按比例瓜分剩餘金額

(b) 會悄悄改掉使用者打的百分比。(a) 讓「你談的跟期程不一致」這件事
**明擺在最後一期上**，那正是需要被看見的訊號。

#### 已請款的凍結，未請款的重算

工程案必有追加減帳，分母會變。兩種做法都錯：

- 設定時算好就凍結 → 追加後所有期別金額都過時
- 永遠重算 → 已請過款的期別金額回頭變動，而帳已經出去了

→ `billedOn` 一寫入該期就凍結，尾差改落到最後一個**未請款**的期別。
同 `advances.balance` 核銷凍結、`contracts.stampDutyRate` 的模式，第三次了。

合約新增／改金額／作廢都會觸發重算（`contracts.ts` 三處呼叫
`recomputeBillings`），使用者不必回頭按一次存檔。

#### 尾差沒地方放時不靜默吞掉

所有期別都已請款或都被人工覆寫時，尾差無處可去。
→ 回 `unallocatedResidue`，UI 紅框顯示「有 N 元無法分配」。
靜默吞掉那筆錢就消失了，而對帳時只會看到合計對不起來。

#### 分母的定義（使用者裁示：含追加減）

`contractTotal` ＝ 我方**承攬**的合約 + 追加減帳（未作廢）：

| 排除 | 理由 |
|---|---|
| 報價單 | 還沒成案 |
| 我方是定作人 | 那是應付，不是應收 |

一張合約都沒有時回 **null 而不是 0**：0 會讓每期算出 0 元、看起來像算過了，
null 才能讓 UI 說「還沒有合約，無法計算」。

分母的組成（主約／追加減）攤開回傳並顯示在 UI 上——
**看不到組成就會有人去開試算表對帳**，那就回到客戶要消滅的東西了。

#### 整批存而不是逐筆 CRUD

改一期的百分比會牽動尾差落點。逐筆存會讓中間狀態出現「合計不等於合約金額」
的假象。`PUT /projects/:id/billings` 一次收整份期程：有 id 更新、無 id 新增、
不在 payload 裡的軟刪除——**已請款的不可移除**（409）。

#### 試算值存進 DB，不是每次即時算

報表與其他模組會直接讀這張表。若只存百分比，每個讀取端都要自己重算一次
尾差，遲早有一個算得不一樣。

#### 保留款不需要另一套機制

前三條各提過一次保留款，客戶四條下來都沒提。做完這條後確認：
**用一個期別就能表達**（末期「保留款」5%，`plannedOn` 填驗收後）。
不必另建欄位。

#### ⚠️ partial unique index 的坑

期別編號要在「未刪除的列」之間唯一。第一版寫成
`uniqueIndex(tenant_id, project_id, installment_no, deleted_at)` —— **是錯的**：
Postgres 視 NULL 互不相等，兩筆 `deleted_at IS NULL` 的列反而不會相撞，
索引等於沒作用。正解是 partial index `WHERE deleted_at IS NULL`。
schema 測試有一條專門盯 `config.where` 存在。

#### 範圍：只做到「請款」

第 1 條記過「請款 ≠ 開票 ≠ 收款」是三個事件。本條只做**計算應收**與
**請款事件**——後者是本條自己的規則所必需（凍結要有觸發點）。

**開票與收款不做**：那要 `invoices` / `receipts` / 開票公司 /
docs/01 第六節的 `requires_review`（集團代收代付），是另一整塊。
不猜那些欄位的形狀，猜錯比之後加欄位更貴。
