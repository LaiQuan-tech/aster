## 7. 已知缺口／後續

- **忘記密碼節流是記憶體內**（`apps/api/src/services/auth-invite.ts` 的 `forgotLastSent = new Map()`）：多個 API instance（Vercel serverless 常態）各自算節流，同一 email 短時間內可能繞過節流打到不同 instance 而觸發多次。
- **被 409 擋下的邀請仍會替對方帳號輪替 recovery token**：`sendEmployeeAccountLink` 為了判斷「這個 email 是否已存在帳號」，一律先呼叫一次 `generateLink({type:'recovery'})` 探測，**探測動作本身就會讓 Supabase 端輪替該帳號的 recovery token**，之後才判斷這個帳號其實屬於別的租戶／員工而回 409——等於一次失敗的邀請呼叫仍對「無關的第三方帳號」造成了一次 token 輪替的副作用，構成輕度 DoS（可能讓對方原本手上還沒用的舊重設連結失效）。
- **實習生六個基準頁沒有頁面級 guard**（§2 A3）：`home/schedule/punches/requests/notifications/mydata` 沒有掛 `EssTabGate`，如果之後把 intern 的預設清單改成不含其中一頁，nav 上的 tab 會消失但直接打網址仍擋不住。

## 9. 開發慣例

- **多 agent 共用一份 working tree**：每個 WP 用 `git add <明確路徑…>`（pathspec）分開 commit，不要整包 `git add -A`，避免把別的 agent 還沒寫完的檔案一起 commit 進去；`git pull --rebase --autostash` 是標準拉取方式，`--autostash` 讓其他 agent 手上未提交的檔案不會擋 rebase。
- **每批次一個 migration owner**：`drizzle-kit` 的自動編號如果同時有兩個人跑 `npm run db:generate` 會撞號，本輪四批次固定 A→0042/sql0031、B→0043/sql0032、C→0044/sql0033、D→0045/sql0034，一個批次只有一個人跑產生指令。
- **正式庫套用流程**：每批次先產 `docs/套用-2026-09-1x-<批次>.sql`＋`docs/驗證-…sql`，本機先用 `npm -w packages/db run replay -- <檔>` 過 PGlite 重放一次，再用 Supabase Management API 整段送正式庫（**單一交易**，中間任何一句錯就整段回滾），驗證 SQL 逐句手動核對，不整段跑。
- **live test 用 throwaway 租戶打正式庫**：純函式測試在本機／CI 跑（`vitest`），需要真的打 API／DB 的合約測試（`__tests__/*-live.test.ts`）建一個用完即丟的租戶，用 `describe.skipIf(!migrated)` 讓 migration 還沒套用時自動跳過而不是紅字失敗。
- **通知走統一的 `notify.ts`**：任何要通知使用者的地方都呼叫 `apps/api/src/services/notify.ts`，不要自己直接寫 `notifications` 表；實際投遞（含要不要寄信）由既有的 `deliver-pending-notifications` 排程負責，沒有另外開投遞管線。Resend 只有 `apps/api/src/lib/resend.ts` 一個呼叫點，之後要換供應商只改這一個檔案。
